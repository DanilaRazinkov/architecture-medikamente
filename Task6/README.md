### 2. Пояснительный документ

#### 2.1. Предлагаемый слой классификации данных

В рамках целевой архитектуры предлагается внедрить **Слой классификации и обогащения данных (Data Classification &
Enrichment Layer)**, который располагается между операционными системами и аналитическим хранилищем. Его цель —
автоматическое определение уровня конфиденциальности входящих данных и их подготовка к безопасному хранению в
соответствии с принципами Privacy by Design.

**Ключевые задачи слоя:**

1. **Интеллектуальный анализ структуры:** Автоматическое обнаружение схемы данных и отслеживание её изменений (новые
   поля, изменение типов). Это критично для работы с legacy-источниками вроде 1С и Excel-файлов.
2. **Контентная классификация:** Анализ не только имён полей, но и фактического содержимого с использованием правил (
   регулярные выражения для РФ: ФИО, телефоны, СНИЛС) и ML-моделей для классификации неструктурированного текста (
   медицинские заключения).
3. **Применение политик:** Каждому полю или записи присваивается тег конфиденциальности (L1-L4) на основе внутренних
   классификаторов и сверки с корпоративными политиками из отдельного хранилища.
4. **Преобразование данных:** На основе тегов данные автоматически направляются в конвейеры обработки:
    * **L4 (Диагнозы, анамнез):** Строгое обезличивание (k-анонимность, дифференциальная приватность).
    * **L3 (ФИО, паспорт):** Токенизация с сохранением ссылочной целостности. Маппинг "токен-значение" хранится в
      отдельном, максимально защищённом хранилище (Vault).
    * **L2 (Телефон, email):** Маскирование (например, `+7 XXX XXX-XX-89`).
    * **L1 (Агрегированные/обезличенные):** Минимальная обработка.

#### 2.2. Организация слоёв хранилища с учётом конфиденциальности

Аналитическое хранилище делится на физически или логически изолированные зоны, соответствующие уровням
конфиденциальности и целям использования:

1. **Raw Zone (L3-L4, зашифровано):** "Сырые" данные, зашифрованные на лету. Используется для аудита и юридических
   целей. Доступ строго по запросу и с полным аудитом.
2. **Restricted Zone (L3, токенизировано):** Данные, где прямые идентификаторы заменены токенами. Позволяет выполнять
   аналитику, сохраняя связи между записями (например, построить цепочку посещений врача одним пациентом). Доступ только
   для авторизованных BI-систем и аналитиков с повышенными привилегиями.
3. **Analytics Zone (L1-L2, обезличенно/агрегировано):** Основная рабочая среда для аналитиков, Data Scientists и
   BI-инструментов. Содержит только обезличенные и агрегированные данные. Доступ максимально открыт внутри безопасного
   периметра.
4. **Public Zone (L1, агрегаты):** Высокоуровневые агрегаты и отчёты для руководства и публичных дашбордов. Не содержат
   никакой ПДн.

**Дополнительные меры безопасности:**

* **Сетевые ACL:** Жёсткие правила firewall между зонами.
* **Ролевой доступ (RBAC/ABAC):** Разные группы доступа для сотрудников (аналитик, врач, бухгалтер).
* **Сквозное шифрование:** Данные шифруются при передаче между зонами и в состоянии покоя.
* **Data Lineage:** Все перемещения данных между зонами фиксируются в каталоге метаданных (Apache Atlas).

#### 2.3. Метрики для оценки эффективности классификации

Для мониторинга и оптимизации работы движка предлагается трекать следующие группы метрик:

| Группа метрик              | Конкретные метрики                                                                                             | Целевое значение                                                                      | Как помогает в оптимизации                                                                                               |
|:---------------------------|:---------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------|
| **Точность классификации** | `accuracy`, `precision`/`recall` по классам L1-L4, F1-score, матрица ошибок.                                   | >95% accuracy, >99% recall для L4 (критично не пропустить диагноз)                    | Выявление систематических ошибок (например, ML-модель путает L3 и L2). Позволяет дообучать модели и уточнять правила.    |
| **Качество обработки**     | Процент данных, успешно прошедших обработку (обезличивание/токенизацию). Уровень достигнутой k-анонимности.    | 100% успешной обработки, k >= 5                                                       | Гарантирует, что в Analytics Zone не попадут необработанные данные. Контролирует эффективность алгоритмов обезличивания. |
| **Производительность**     | Пропускная способность (записей/сек), задержка (latency) обработки, использование ресурсов (CPU, RAM).         | Пропускная способность, соответствующая пиковой нагрузке (например, 5000 записей/сек) | Помогает планировать масштабирование инфраструктуры и выявлять "узкие места" в конвейере.                                |
| **Соответствие политикам** | Процент данных, маршрутизированных в корректную зону хранилища. Количество инцидентов с некорректным доступом. | 100% корректной маршрутизации, 0 инцидентов                                           | Является прямой метрикой выполнения требований безопасности и законодательства (152-ФЗ).                                 |

**Процесс оптимизации на основе метрик:** Метрики в реальном времени отображаются в Grafana. При падении `recall` для
класса L4 срабатывает алерт. Команда анализирует выборку ложно-отрицательных случаев, выявляет причину (например, новый
формат записи диагноза), корректирует правила или дообучает ML-модель, а затем проверяет рост метрики на тестовом
наборе.

#### 2.4. Обеспечение масштабируемости системы

Архитектура движка и хранилища заложена как горизонтально-масштабируемая с расчётом на пятикратный рост данных и
открытие филиалов.

**Масштабирование движка классификации:**

1. **Микросервисная архитектура:** Каждый компонент (приёмник, классификатор, обработчик) — отдельный сервис в
   Kubernetes, масштабируемый независимо.
2. **Очереди сообщений (Kafka):** Разделяют этапы конвейера, позволяя им работать асинхронно и с разной скоростью.
   Увеличение количества партиций топиков и consumer'ов позволяет линейно наращивать пропускную способность.
3. **Статусная и безстатусная обработка:** Тяжёлые компоненты (ML-классификация, обезличивание) проектируются как
   безстатусные, что позволяет легко добавлять их инстансы под нагрузку.
4. **Кэширование:** Часто используемые справочники (политики, правила, словари) кэшируются в Redis для снижения нагрузки
   на БД и ускорения обработки.

**Масштабирование хранилища:**

1. **Шардирование и партиционирование:** ClickHouse-кластер для каждой зоны хранилища масштабируется добавлением
   шардов (для распределения данных) и реплик (для отказоустойчивости и чтения). Данные партиционируются по времени (
   например, по месяцам).
2. **Геораспределение для филиалов:** При открытии нового филиала возможна организация локального edge-узла для
   предобработки и первичного обезличивания данных с последующей синхронизацией агрегированных результатов в центральное
   хранилище. Это снижает сетевой трафик и задержки.
3. **Эластичность в Kubernetes:** Использование Horizontal Pod Autoscaler для автоматического добавления подов
   классификатора при росте очереди в Kafka и Cluster Autoscaler для увеличения количества нод в кластере Kubernetes.

**План масштабирования:**

* **Старт:** Все сервисы в одном Kubernetes-кластере, ClickHouse из 3 нод.
* **Рост (x5):** Увеличение числа реплик сервисов и добавление шардов в ClickHouse.
* **Экспансия (филиалы):** Развёртывание периферийных кластеров обработки в филиалах, централизованное хранилище
  метаданных и политик.

### Архитектура «Медикаменте» с Privacy by Design: Целевое состояние (To-Be)

#### Ключевые архитектурные блоки Privacy by Design

Для устранения критических рисков, выявленных ранее (хранение медкарт в открытом виде, отсутствие шифрования и контроля
доступа), в ядро системы добавляется специализированный **Privacy Layer** (Слой Конфиденциальности).

| **Компонент Privacy Layer**                              | **Решаемая проблема из As-Is**                                            | **Принцип Privacy by Design**                                               |
|:---------------------------------------------------------|:--------------------------------------------------------------------------|:----------------------------------------------------------------------------|
| **Сервис управления согласиями (Consent Mgmt)**          | Обработка ПДн без явного согласия пациентов; отсутствие механизма отзыва. | Уважение к приватности пользователя; Конфиденциальность по умолчанию.       |
| **Сервис контроля доступа (Access Control - ABAC/RBAC)** | Принцип «всем всё»: доступ IT-отдела и врачей ко всем данным.             | Минимальные привилегии; Защита данных на протяжении всего жизненного цикла. |
| **Сервис шифрования (Encryption Service)**               | Хранение и передача данных (включая интеграцию ККМ-1С) в открытом виде.   | Полнофункциональность; Защита на всех этапах.                               |
| **Сервис аудита (Audit Service)**                        | Невозможность отследить, кто и когда обращался к конфиденциальным данным. | Видимость и прозрачность.                                                   |
| **Сервис обезличивания (Anonymization Service)**         | Использование полных ПДн для аналитики, создающее риск реидентификации.   | Минимизация данных.                                                         |

Этот слой становится **центральным элементом** (hub) всей системы. Все запросы к данным, от просмотра медицинской карты
врачом до интеграции с лабораторией, проходят через него для проверки согласий, прав доступа и обязательного
логирования.

#### Аналитический слой с учётом Privacy by Design

Для безопасной работы с данными в BI/ML/AI целях проектируется изолированный **Analytics Layer**. Его ключевое отличие
от текущего состояния — **полное отсутствие прямых персональных данных**.

**Принцип работы аналитического слоя:**

```
Операционные данные (EMR, CRM)
        ↓
[ETL-процесс с обезличиванием]
        ├─ Удаление прямых идентификаторов (ФИО, телефон)
        ├─ Обобщение квази-идентификаторов (дата → возрастная группа)
        ├─ Применение k-анонимити (k=10)
        └─ Регистрация метаданных и Data Lineage
        ↓
    Data Lake / Analytics DB
        ↓
    BI-панели
    ML-модели
```

**Реализованные принципы:**

* **Минимизация данных**: В аналитику попадает только минимум необходимых, обезличенных полей.
* **Разделение обязанностей**: Аналитики получают доступ только к Data Lake, полностью изолированному от операционной
  БД.
* **Прозрачность (Data Lineage)**: Использование каталога данных (например, Apache Atlas) позволяет отследить
  происхождение любого набора данных в аналитике.
